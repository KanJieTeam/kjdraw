# Token-efficiency claim protocol (draft, frozen before live evaluation)

KJDraw may claim **“fewer total model tokens on at least 99% of tasks”** only after a public, prespecified evaluation meets the rules below. Shorter CLI output, smaller tool schemas, lower cost on one category, or a faster but invalid drawing do not satisfy this claim. The task manifest, scorer and arm implementations must be committed before running the scored models; changes after seeing results create a new version and restart the evaluation.

## Tasks and arms

- Use at least 100 distinct, versioned tasks, including small one-shot geometry, complete professional sheets, and sequential multi-round edits. Keep a separate unseen holdout and disclose task counts by category. Do not inflate the count by renaming one parameterized task many times without disclosing its family.
- Give both arms identical engineering requirements, input files, revision history and model provider/version. The KJDraw arm may use the documented Skill/CLI and deterministic CAD compilers. The comparator may use Python plus `ezdxf`, calculations, loops, functions and ordinary local files; do not force it to hand-write raw DXF. Neither arm receives a hidden answer or hand-edited geometry.
- Model-generated Python is untrusted code. The existing restricted worker is **not** an OS sandbox and requires review of each exact source hash before execution. A scored unattended run needs a genuinely isolated executor or a separately declared, safe structured-CAD comparator; it must not silently bypass that review just to finish the corpus.
- For multi-round tasks, send each instruction only after the previous round is produced. Evaluate every intermediate drawing and the final drawing, including object identity, untouched geometry, dimensions, units, revision and export/reopen properties where applicable. Count the entire conversation, tool definitions loaded, tool outputs returned to the model, follow-up inspection and all retries.

## Fixed run conditions

Run each model and task at least three times per arm, with the same temperature/thinking setting, output cap, timeout, prompt information and retry policy. Alternate arm order. Record model IDs returned by the provider, cache read/miss usage when supplied, total input/output/reasoning tokens as reported, wall time, tool calls, and failure/timeout reasons. A missing usage record stays missing; do not estimate it from bytes or silently discard it. Stop on provider budget or quota errors and publish the unexecuted tasks.

Use independent CAD validators, not the model's own success statement. Save sanitized request/response metadata, source hashes, generated KJD/DXF, scorer outputs, exact dependencies and replay commands. Keep API keys and customer drawings out of the evidence archive. No manual repair is allowed in either arm during a scored run.

## Primary decision rule

For each named model, the denominator is **every task in the frozen manifest**. A task is a token-saving win only when all three KJDraw runs and all three comparator runs produce valid drawings at every required round, all six have complete provider-reported token usage, and the KJDraw median cumulative total token count is strictly lower than the comparator median. A tie, missing measurement, invalid drawing, timeout or unexecuted task is **not a win**. For 100 tasks, the threshold is at least 99 wins; for `N` tasks it is `ceil(0.99 × N)`. Report the actual numerator, denominator and per-category rates for each model. Do not pool providers to conceal a weak model.

Publish validity, median and total token counts, per-round drift, latency and estimated price (if rates are documented) separately. State clearly whether prompt caching was enabled and whether token counts include reasoning. The claim must name the evaluated model versions, corpus version and date; it is not a guarantee for all CAD tasks or future models.

Current evidence does **not** meet this protocol: the basic-tool simple pilots used more tokens on all six paired tasks, while the 30-task manufacturing result used a narrower raw-DXF baseline and only one completed provider run. The new CLI `--summary` experiment measures response **bytes**, not model tokens. These results remain published as counterexamples and hypotheses, not converted into a 99% claim.

The current frozen 100-task diagnostic corpus is parameterized: **six simple-drawing families × five variants, one fixture-sheet family × thirty variants, and eight edit families × five variants**. It has 180 rounds, not 100 unrelated drawing archetypes. This family structure is disclosed rather than presented as broader coverage. A separate unseen holdout and independent user/model review are still outstanding; even a favorable result on this corpus alone would need that qualification.

## Reproduce the current harness

With Node.js 22+, Python and `ezdxf` available locally, run `node scripts/benchmarks/token-efficiency-plan.mjs` to see the frozen 100-task/180-round/3-model/3-repetition denominator without contacting any provider. Run `node --test packages/kjdraw-sdk/test/token-efficiency-task-corpus.test.mjs packages/kjdraw-sdk/test/declarative-ezdxf-baseline.test.mjs packages/kjdraw-sdk/test/token-efficiency-scorer.test.mjs packages/kjdraw-sdk/test/token-efficiency-checkpoint-cli.test.mjs` to exercise the corpus, both CAD arms, independent scorer and resume path with fixtures. `KJDRAW_CORPUS_FULL_VALIDATION=1` enables the slower exhaustive corpus validation.

The checkpoint CLI takes an absolute JSON config path and an absolute output directory. A config for the full protocol has `{"models":[{"provider":"deepseek","model":"deepseek-chat","settings":{"temperature":0,"max_tokens":4096}},{"provider":"qwen","model":"qwen-plus","settings":{"temperature":0,"max_tokens":4096}},{"provider":"glm","model":"glm-4.5","settings":{"temperature":0,"max_tokens":4096}}],"repetitions":3,"interfaceMode":"skill-json"}`. Verify each exact model ID and settings against the provider before running; a returned-model drift stops the run. The read-only command is `node scripts/benchmarks/token-efficiency-checkpoint-cli.mjs --config=<absolute-config.json> --output=<absolute-results-directory>`.

A paid run additionally requires `--run --confirm-paid --review-gate=<absolute-trusted-review-module.mjs> --review-gate-sha256=<SHA-256-of-that-file>`. The module must export `reviewProposal` and independently decide each KJDraw proposal; a fixture auto-approver is not valid live evidence. Provider credentials are read from `KJDRAW_DEEPSEEK_API_KEY`, `KJDRAW_QWEN_API_KEY` and `KJDRAW_GLM_API_KEY` in the process environment, never from the config or published artifacts. An optional `KJDRAW_BENCH_PROXY` uses an HTTP CONNECT proxy. The output is single-writer and resumes only units whose plan, evidence and DXF hashes still match; changing code or settings requires a fresh results directory. This CLI and the pilot script do not by themselves certify independent review or the 99% claim.
