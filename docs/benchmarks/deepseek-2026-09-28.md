# DeepSeek Flash CAD study — 2026-09-28

This is a reproducible **single-model, synthetic** study, not evidence that KJDraw always saves tokens or that generated drawings are safe for production. It includes favorable and unfavorable results. A model response counts as successful only after independent `ezdxf` parsing, audit, unit and exact task-geometry checks; the manufacturing task additionally checks its full drawing contract.

## Results

All model requests used `deepseek-flash`, non-thinking mode, temperature 0, and no retries or manual correction. Token counts are provider-reported **input plus output** totals. Each one-shot row contains three fully specified tasks—mounting plate, bolt flange, stepped profile—run five times per arm. The direct baseline emits a complete ASCII DXF without a CAD library.

| One-shot route | KJDraw pass | Direct DXF pass | KJDraw tokens | Direct DXF tokens | Interpretation |
| --- | ---: | ---: | ---: | ---: | --- |
| Full `cad_propose_drawing` schema | 15/15 | 8/15 | 39,635 | 7,804 | Reliable here, but **5.08× more tokens** than direct DXF. |
| Existing `cad_propose_drawing_compact` schema | 15/15 | 6/15 | 27,315 | 7,758 | Less overhead than full schema; still **3.52× more tokens**. |
| Compact geometry JSON + KJDraw validation | 15/15 | 7/15 | 4,640 | 7,788 | **40.4% fewer tokens** in this bounded protocol; this is a benchmark host adapter, not a measured end-to-end Skill session. |

The compact-JSON host inserts trusted revision and units, fills omitted empty geometry groups, and passes the model's geometry to the real `cad_propose_drawing_compact` engine. It never executes model code. An initial exploratory run accidentally failed to fill empty groups; its original report was retained, the saved answers were replayed, and the table above uses a **fresh 30-request run after the fix**.

| Persistent 10-edit task | KJDraw pass | Direct DXF pass | KJDraw tokens | Direct DXF tokens |
| --- | ---: | ---: | ---: | ---: |
| Small selected-tool schema | 10/10 | 10/10 | 14,426 | 44,401 |
| **Unmodified production tool definitions** | **10/10** | **10/10** | **18,098** | **47,525** |

The second row is the relevant SDK-tool result: 61.9% fewer tokens than re-emitting the whole DXF on each edit. Both arms were equally accurate on this simple sequence. One sequence and one run per schema are not enough to establish an accuracy advantage or a stable population estimate. The task changes named holes and a guide line, adds two circles and one line, and checks every intermediate DXF. KJDraw KJD state is saved and reopened on every edit. Synthetic harness approval is **not** human review.

| Harder case, five runs per arm | KJDraw pass | Direct DXF pass | Important boundary |
| --- | ---: | ---: | --- |
| Two-view installation plate with native dimensions, generic annotated tool | **0/5** | **0/5** | KJDraw rejected model-generated reference geometry; direct DXF failed structure validation. Do not claim this workflow is solved by the generic tool. |
| 96-hole ISO A2 manufacturing sheet, matching high-level compiler | **5/5** | **0/5** | KJDraw used 3,023 tokens per successful request; direct DXF used 33,409 tokens per failed request under the common 32,768-output-token cap. This does **not** prove direct DXF would fail with unlimited output. |

The 96-hole KJDraw artifact independently passed checks for 409 editable entities, 96 working holes, four mounting holes, two slots, 11 native dimensions, 19 notes and zero DXF audit errors/fixes. The paired direct arm was capped at 32,768 output tokens for both routes. A separate, single-request direct-DXF sensitivity check raised the cap to 131,072 output tokens; the response consumed 131,713 total tokens, ended with `finish_reason=length`, and failed independent DXF structure validation. It took 306 seconds. This additional failure is **not** part of the paired five-run result and still does not prove an uncapped direct route cannot succeed.

After inspecting the failed engineering tool calls, we clarified the model-facing schema and validator error: proposal group references such as `polyline:0` and polyline vertex indexes are **zero-based**. We reran the **unchanged engineering task and acceptance checks** for five fresh paired repetitions. Both arms still scored **0/5**. The KJDraw arm now materialized a DXF in two runs, but each failed the independent `TEXT_LAYER_OR_PLANE` check; the other three proposals were rejected before approval. The direct arm failed DXF structure validation five times. The KJDraw arm used 50,621 total tokens versus 29,556 direct tokens. This rerun is a separate negative result, not a replacement for the original row. A clearer schema alone did not solve full two-view manufacturing annotation.

A later SDK change added whole-group style references and conventional `NOTES` / `DIMENSIONS` defaults for otherwise unassigned annotations, while preserving explicit assignments. Offline replay of the two saved materializable tool calls then passed the text-layer check but still failed with `MISSING_OR_INACCURATE_GEOMETRY`. This **does not change the 0/5 live result** or establish a new model success rate. The saved-call [engineering replay script](../../scripts/benchmarks/replay-annotated-engineering.mjs) makes this narrower finding reproducible without another model call.

We also ran five **fresh** paired repetitions after that SDK change, with the same engineering task, scorer, model and output cap. The KJDraw arm was **0/5** at 52,538 total tokens and the direct-DXF arm **0/5** at 28,637 total tokens. All five new KJDraw proposals were rejected before approval because their native dimension references produced degenerate measurements; all five direct outputs failed DXF structure validation. Offline replay identifies dimension 6 (`ROTATED`) in every repetition: the model chose the same `polyline:0` vertex 0 for both measurement endpoints. This is a third separate negative result. It shows that layer defaults alone do not make the generic one-shot annotation tool a reliable compiler for a complete two-view part.

Local, non-model regression: the full Windows suite passed 1,743 tests with zero failures and two conditional skips after the third engineering run, with `ezdxf` explicitly available. Earlier focused SDK, CLI and benchmark tests passed 53/53; a five-repeat, four-task deterministic strategy benchmark passed 40/40. In its 209-entity panel, batching four proposals had an 85.8 ms median build time versus 3,527.7 ms for 209 per-entity proposals on this non-isolated workstation. These milliseconds are **not model latency or token savings**.

## Method and limits

- Source base: `15929cb`; benchmark scripts and data are committed with this report. Environment: Windows, Node 22.18.0, Python 3.12.7, `ezdxf` 1.4.4, `httpx` 0.27.0. No other model, operating system or independent tester is represented.
- The one-shot direct baseline is intentionally narrow: it does not use an alternative CAD library or DXF serializer. A strong library-assisted agent is a necessary future baseline.
- One-shot tasks and the 10-edit sequence are small and synthetic. The manufacturing task is a synthetic specification, not manufacturing approval. Geology, architecture, roads, imports, fonts, printing, DWG and real customer drawings are **not** evaluated here.
- Scores come from generated files, not screenshots. A DXF that looks plausible but fails parsing, units, exact geometry or the manufacturing contract is a failure. Failed responses remain in the evidence; no result was manually repaired.
- Per-run HTTP requests and model responses were retained **without Authorization headers**. The user-provided API key is not in the data. Never commit your own key. This key was shared in a chat and should be rotated.
- Provider-reported tokens include supplied tool schemas, but the compact-JSON route excludes the full overhead of loading the KJDraw Skill and running a real user client. It must not be advertised as an end-to-end Skill saving.

## Reproduce

From the repository root, install the pinned benchmark dependencies and run the offline checks first:

```sh
python -m pip install -r scripts/benchmarks/requirements.txt
python scripts/benchmarks/deepseek-drawing-pilot.py --self-test
python scripts/benchmarks/deepseek-multiturn-pilot.py --self-test --schema production
node --test packages/kjdraw-sdk/test/agent-drawing-compact.test.mjs packages/kjdraw-sdk/test/agent-cli.test.mjs
```

For a live run, use your own DeepSeek key through stdin; do not put it in a command line, repository file or issue. For example, in PowerShell:

```powershell
$secret = Read-Host -AsSecureString
$plain = [System.Net.NetworkCredential]::new('', $secret).Password
$plain | python scripts/benchmarks/deepseek-oneshot-study.py --live --api-key-stdin --drawing-tool json
$plain | python scripts/benchmarks/deepseek-multiturn-pilot.py --live --api-key-stdin --schema production
$plain = $null
$secret = $null
```

The one-shot command is capped at 30 requests; the multi-turn command at 20. Both stop on transport/authentication errors without retrying. Their output directories contain the exact prompts, responses, DXFs and reports. `scripts/benchmarks/replay-oneshot-study.py <run-directory>` independently rematerializes saved responses without another model call. The more complex manufacturing and engineering suites use `scripts/benchmarks/paired-model-benchmark.mjs` with explicit model, endpoint, selected drawing tool and request budget; inspect its dry-run plan before opting in to a live run.

The [evidence archives](evidence/2026-09-28-deepseek-flash/README.md) contain the raw reports and artifacts, with per-archive SHA-256 digests. The source and failed cases are deliberately included so readers can challenge the benchmark, not just quote its best row.

The scheduled [offline benchmark replay](../../.github/workflows/benchmark-replay.yml) checks saved decisions daily without calling a model or using an API key. It catches engine/validator regressions; it is **not** a new daily model measurement and cannot establish current provider behavior. Fresh paid-model runs remain manual and explicitly budgeted.
