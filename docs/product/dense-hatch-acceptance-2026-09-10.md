# Dense HATCH screen coverage — 2026-09-10

Some valid patterns have an almost collinear row offset. Enumerating their original lines exhausts the vector work budget even when the visible result is small. The new sampler changes the integer basis of the original dash lattice to test stroke coverage directly. It preserves row spacing, dash period and phase; it does not increase spacing or substitute a solid fill.

When vector enumeration is limited, the Canvas renderer may construct a bounded physical-pixel mask with four subpixel samples per pixel. It clips that mask against the existing even-odd boundary and applies the drawing's color and transparency once. The original vector path remains available. Any unknown sample rejects the mask and retains a partial diagnostic; unsupported dots, numeric uncertainty and pixel/work limits remain explicit. This is a screen rasterization strategy, not a vector export or exact antialiasing claim.

Per-frame limits bound pixels and candidate work. The cache holds at most eight entries and 32 MiB, keyed by immutable source geometry, view, pixel ratio, line width and color. Block instances include their complete bounded transformation chain. Changes invalidate the corresponding entry; stable views reuse it. Large visible regions can still exceed the limits and must remain partial.

Validation includes original-row oracle comparisons over millions of rows, retained dash gaps, continuous and multiple families, negative offsets, transformed patterns, uncertainty and work bounds. Renderer tests cover cache eviction, payload changes, allocation limits and block instances. Focused Chromium checks cover DPR 1/2, gaps, holes, 50% transparency, pan/zoom and unchanged document bytes; no local three-browser matrix was run.

A private local regression inspected 183 non-solid model-space hatches at a 640×400 CSS viewport and DPR 1. All retained actual pattern pixels, with zero unsupported or partial diagnostics. The same import reproduced the four formerly limited cases through the original vector method; all four then rendered at DPR 2 without partial diagnostics. Their observed first render took 6.6–18.9 ms at DPR 1 and 24–36.5 ms at DPR 2; cached frames took 0.02–0.04 ms and 0.06–0.08 ms respectively. These are measurements of this local run, not performance guarantees. Documents remained byte-identical, with no page errors or external requests. Private geometry, names, paths and screenshots are not distributed.

Passing this regression does not establish complete HATCH/OCS/export support, unrestricted large-canvas performance, full drawing fidelity or stable 1.0 readiness.
