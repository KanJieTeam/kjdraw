# KJDraw 1.0 independent readiness audit — 2026-09-08

This audit records the repository state at commit `f1fccba` before the planned 1.0 implementation. It is a release gate, not launch copy. A passing unit-test count is necessary but cannot certify broad CAD compatibility, interactive performance, security, or product maturity.

## Verdict at baseline

**A production/stable 1.0 would not be honest at this baseline.** The repository is a credible developer preview with several unusually strong foundations: deterministic document transactions, explicit preservation checks, a real ZIP64 project package, a small Rust/WASM authority, and review-bound Agent command plans. Its own [acceptance matrix](../KJDRAW_1_0_ACCEPTANCE_MATRIX.json) correctly marks TypeScript ownership, DXF compatibility, geometry authority, editing and plugin isolation as partial; plotting and DWG are blocked.

The appropriate release sequence is: close the P0/P1 evidence gaps, publish a release candidate, collect independent compatibility and usability feedback, then promote the exact tested artifact to 1.0. Changing the version string alone would weaken trust.

## Reproduced evidence

| Gate | Baseline result | Scope and limitation |
| --- | ---: | --- |
| JavaScript SDK tests | 93/93 passed | Mostly deterministic unit/integration tests in Node; no coverage or mutation score |
| Rust tests | 15/15 passed | Primitive geometry, document authority, spatial helper and bounded solid-mesh scope |
| TypeScript ownership | 2 generated modules passed parity | Remaining public implementation is JavaScript-owned; declarations are hand-maintained |
| DXF corpus | 7/7 passed | Seven three-entity synthetic ASCII fixtures; not independent CAD interoperability evidence |
| Release hygiene | 166 files passed | Local links, exports, excluded paths and credential-shaped strings only |
| Static build | passed | Produces the playground/docs; not a production bundle or framework integration build |
| npm package | dependency-free runtime | Ships source JavaScript and handwritten declarations; no compiled `dist`, source maps, or conditional type exports |
| CI matrix | Node 22/24 on Windows/macOS/Linux | No browser matrix, mobile/touch, accessibility, visual regression, performance budget, coverage, fuzzing, or long-running soak job |

At the baseline, `src/index.js` exposes 183 runtime names through wildcard exports. A conservative name-presence check found more than 130 of those names absent from the handwritten `types/index.d.ts`, including registries, adapters, geometry utilities, WASM sessions and plugin contracts. The declaration test only checks a handful of selected names, so it cannot establish runtime/type parity. Subpath exports also lack explicit `types` conditions.

The synthetic benchmark on this audit host (Windows x64, Node 24.19.0, 32 logical CPUs) produced the following single-run results. They are diagnostic evidence, not portable claims:

| Lines | Batch creation | Move one entity | Snapshot | KJD size | End RSS |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1,000 | 174 ms | 145 ms | 17 ms | 0.95 MB | 137 MiB |
| 10,000 | 2,386 ms | 2,076 ms | 213 ms | 9.49 MB | 606 MiB |

The growth is consistent with the current full-document clone/validation and full before/after undo snapshots in the transaction path. It is a hard blocker for claims of large-drawing interactive performance until an architectural fix and browser measurements exist.

Reproduce the existing gates:

```bash
node scripts/test.mjs
node --no-warnings scripts/build-typescript.mjs --check
node scripts/audit-dxf-corpus.mjs
node scripts/check.mjs
node scripts/build.mjs
cargo test --locked --manifest-path runtime/kjcore-rs/Cargo.toml
```

Run the new non-certifying synthetic core benchmark with a named entity count:

```bash
node scripts/benchmarks/core-readiness.mjs --entities=10000
```

Inspect the machine-readable release gate (add `--require-ready` to make open gates fail the command):

```bash
node scripts/audits/release-readiness.mjs --require-ready
```

The audit automatically fails a stable `1.x.y` version when the acceptance matrix contains an unpassed gate, preventing a version-only promotion.

## Release blockers

### P0 — required before an honest stable package

1. **Finish TypeScript ownership and build the public artifact.** Make strict `.ts` the single source for every public module; generate ESM plus declarations and source maps into `dist`; compile the React and Vue examples in CI. Remove duplicate handwritten implementation/declaration authority. Compile consumer fixtures against every root and subpath export from the packed tarball so runtime/type parity is measured rather than sampled.
2. **Define and enforce the stable API contract.** Add package export/type tests against the packed tarball, API-report or declaration-diff gating, documented deprecation rules, and migration fixtures. Test the lowest supported Node/browser versions, not only current Node 22/24.
3. **Create real renderer and interaction evidence.** Add Playwright coverage in Chromium, Firefox and WebKit for open/draw/select/snap/edit/undo/save/reopen/export, keyboard-only use, Chinese/English switching and responsive layouts. Add deterministic visual regression for representative drawings.
4. **Publish measurable performance budgets.** The document transaction path clones and validates the complete document and stores complete before/after history for each edit. Establish budgets for first render, pan/zoom frame time, hit-testing, a single edit, save/reopen and peak memory at 10k/50k/100k entities; move expensive geometry and parsing off the UI thread where needed.
5. **Replace synthetic-only compatibility claims.** Build a redistributable, independently sourced DXF corpus with expected semantics and round-trips through at least two external applications. Include damaged/truncated/oversized inputs, encodings, bulged polylines, blocks/attributes, dimensions, hatches, layouts, fonts and proxy records.
6. **Close input-resource limits.** DXF and KJD reads currently materialize the full input and have no documented byte/tag/object/depth limits. KJP defaults allow 100,000 entries and 8 GiB expanded content, which is unsafe as a browser default. Add conservative host-configurable budgets, cancellation, timeouts and adversarial tests.
7. **Make release provenance actually enforceable.** The npm workflow requests provenance but lacks the [`id-token: write` permission required by npm](https://docs.npmjs.com/generating-provenance-statements/); add trusted publishing or narrowly scoped OIDC, [pin third-party Actions by immutable commit](https://docs.github.com/en/actions/security-for-github-actions/security-guides/security-hardening-for-github-actions#using-third-party-actions), generate an SBOM, scan dependencies/licenses, and publish checksums. Existing annotated tags are not cryptographically signed.
8. **Resolve 1.0 product-contract contradictions.** The project package currently writes `minReaderVersion: 1.0.0` and `writerVersion: 1.0.0` while the shipping SDK is `0.7.2-preview.1`. Generate these fields from the artifact version and add forward/backward compatibility tests.
9. **Set a support and vulnerability policy.** Document supported versions, coordinated disclosure expectations, response targets, release ownership, backup maintainers and an end-of-life policy. “No SLA” is reasonable for preview but insufficient for a production claim.
10. **Use a release candidate and independent acceptance.** Freeze `1.0.0-rc.1`, publish exact Demo/Docs/npm/GitHub assets, recruit external integrators, triage their findings, and promote the same tested commit only after all required gates are evidenced.
11. **Strengthen Agent approval binding.** The current document fingerprint and reviewed-argument binding use 64-bit FNV-1a. That checksum is useful for deterministic change detection but is not collision-resistant security. Version the binding algorithm and use SHA-256 at minimum; for cross-process authorization, require a host-keyed MAC or signed approval token and persist the reviewer/audit record outside the in-memory SDK.

### P1 — required for the launch to feel complete

- Ship framework-native React and Vue packages or explicitly label the current examples as adapter snippets; compile and execute both.
- Add a CLI for headless validate/inspect/convert/benchmark workflows.
- Provide a versioned API reference generated from TypeScript, not only prose documentation.
- Supply three compelling, openly licensed sample projects with guided tasks and downloadable outputs.
- Add a plugin starter, compatibility test harness and one end-to-end reference plugin.
- Add governance, maintainer/security roles, `SUPPORT.md`, `GOVERNANCE.md`, issue forms, feature request/RFC templates, `CODEOWNERS`, Dependabot/Renovate and a public release checklist.
- Provide browser support, accessibility and internationalization matrices with tested status.
- Clarify plotting: either ship tested SVG/PDF/print output or explicitly remove plotting from the stable contract.
- Keep DWG and general BRep outside the 1.0 promise unless an authoritative implementation and legal redistribution story exist.

## Differentiation worth concentrating on

KJDraw should not market itself as a smaller [FreeCAD](https://github.com/FreeCAD/FreeCAD) or [LibreCAD](https://github.com/LibreCAD/LibreCAD). Mature projects already cover desktop CAD breadth: FreeCAD has an OpenCascade-based parametric kernel and broad workbenches, while LibreCAD has conventional 2D workflows, format conversion and extensive translations. Browser-first libraries such as [JSCAD](https://github.com/jscad/OpenJSCAD.org) and [Maker.js](https://github.com/microsoft/maker.js) already offer modular npm geometry, live playgrounds and multiple export paths; [replicad](https://github.com/sgenoud/replicad) and [Bitbybit](https://github.com/bitbybit-dev/bitbybit) expose OpenCascade/other kernels to TypeScript applications.

The defensible KJDraw wedge is the combination below:

1. **Auditable Agent-native editing:** exact plan arguments, document fingerprint/revision binding, human review, one-shot execution, receipts and undo shown visually as a geometry diff.
2. **Application-grade CAD state:** durable project/document contracts, atomic transactions and preservation-aware round trips rather than only generated geometry.
3. **Deployment-neutral architecture:** the same public core works browser-local, desktop/self-hosted and server-accelerated through explicit providers, with no implicit network dependency.
4. **Familiar bilingual engineering workbench:** users can understand the product immediately, while integrators can progressively adopt the headless SDK, renderer, framework bindings and Agent protocol.

The launch demo should tell one concise story in under 90 seconds: open a non-trivial drawing, ask an Agent for a meaningful change, inspect the exact geometric diff and safety binding, approve once, undo, save the project, reopen it, then embed the same drawing in React or Vue. That is both credible and notably different from a generic browser drawing demo.

## Promotion gate

Release `1.0.0` only when every P0 item has linked executable evidence, the acceptance matrix contains no `blocked` item inside the advertised 1.0 scope, the packed npm artifact passes clean-install tests, and the public Demo/Docs are verified from the exact release commit. Popularity cannot be guaranteed by engineering, but trust, a sharp differentiated story, instant hands-on value and low-friction contribution can be engineered and measured.
